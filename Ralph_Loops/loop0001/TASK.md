# TASK: Machine learning to understand the nature of MOSP — phase 1

## Philosophy
- This loop produces **findings about the problem**, not solver components. Read
  `reports/ml_nature_plan.md` §0 and §4 before anything else; it is the plan this
  loop executes, and `reports/learning_plan.md` §4 lists what is closed and must
  not be rebuilt (learned upper bounds, learned lower bounds, learned branching).
- **A prediction is never a bound.** Nothing learned may touch
  `satisfiability/mosp_solver.py::_lower_bound` or any path that decides `k`.
- **Every split groups by `source_file`**; where the question is about scale,
  group by size. Report grouped numbers; random-split numbers only beside them.
- **State the size range every conclusion covers.** 5,938 of 6,376 instances have
  ≤ 30 customers.
- Every number in a report is regenerated by a command named in that report.
- Findings that rest on a handful of instances are re-certified for those
  instances (`solve_mosp_exact`, never `solutions_dir=None`) before being written.

- **Compute**: a `benchmarks.recertify` run is using 4 cores and must not be
  touched (PIDs under `pgrep -f benchmarks.recertify`). 32 cores total; use up
  to 16 here. An RTX 5090 with CUDA is available for the GNN check or anything
  else that benefits (`torch` may be added behind a soft import). Each iteration
  has a hard 3-hour wall-clock cap enforced by the driver; budget the study so
  the report section and PROGRESS.md are written well inside it, and sample if
  the full study would not fit, saying so in the report.

## Acceptance Criteria (per item)
- [ ] Code lives under `learning/` with a module docstring saying what question it
      answers and how to run it; runnable as `python -m learning.<name>`.
- [ ] A section appended to `reports/ml_nature.md` (create it on the first
      iteration) with: the question, the method, the baseline, the table(s), the
      finding in one paragraph, the size range covered, and the regenerate command.
- [ ] `python -m pytest tests/ -q -x` passes (66 s). New code that computes a
      quantity gets at least one test on a tiny hand-checkable instance.
- [ ] The item is marked `- [x]` (done) or `- [!]` (blocked, with a reason in
      PROGRESS.md) in `iterations.md`.
- [ ] No regressions, no changes to solver defaults, nothing written to `solutions/`.

## Completion Conditions
An item is DONE when either:
1. **Solved**: meets all criteria and the report section is written, OR
2. **Blocked**: documented in PROGRESS.md with the specific blocker.
