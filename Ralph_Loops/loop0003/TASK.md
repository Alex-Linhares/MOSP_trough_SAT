# TASK: Machine learning to understand the nature of MOSP — phase 3, objects

## Philosophy
- This loop produces **objects**: checkable certificates, a conjectured bound
  with a counterexample engine, a measured speed-up, two measured search rules,
  a synthesis. Read `reports/ml_nature_plan_2.md` in full first (it is the plan
  this loop executes and §0 lists what the first two loops established), then
  the sections of `reports/ml_nature.md` your item cites, and `CLAUDE.md`'s
  "What the corpus says about the problem itself" and "The generated-ensemble
  campaign". `reports/learning_plan.md` §4 lists what is closed and must not be
  rebuilt: learned upper bounds, learned lower bounds, learned branching,
  single-witness imitation.
- **A prediction is never a bound.** Nothing learned may touch
  `satisfiability/mosp_solver.py::_lower_bound` or any path that decides `k`.
  A conjectured bound is written up as a conjecture, checked on every certified
  instance, attacked by the extremal search, and never used by the solver.
- **No solver default changes.** Fan order, Theorem 2's switch, the relabelling
  portfolio and the rule are measured behind flags that default to today's
  behaviour, with paired node counts, and *proposed* in the report. Enabling
  any of them is the owner's change.
- **Every split groups by file ∪ MOSP-graph isomorphism class**
  (`learning.fingerprint.union_groups`; certificates in `learning/data/canonical.csv`
  and `learning/data/ensemble/results.csv`).
- **Nodes, not seconds**, for every hardness statement; seconds beside them.
  A censored call (deadline) is a lower bound, never a missing value.
- **State the size range every conclusion covers.** The corpus is 6,376
  instances at 9–134 customers; the campaign is 37,800 at 10–40; item 02
  extends it to 75 and, on the ridge, 100. Nothing below 100 is evidence about
  125×125 except through a stated extrapolation.
- Every number in a report is regenerated by a command named in that report.
- Findings that rest on a handful of instances are re-certified for those
  instances (`solve_mosp_exact`, never `solutions_dir=None`) before being written.

- **Compute**: check `pgrep -f benchmarks.recertify`; if it is running, its
  cores are not yours. 32 cores total; use up to 16 here. An RTX 5090 with CUDA
  is available. Each iteration has a hard 3-hour wall-clock cap enforced by the
  driver; budget so the report section and PROGRESS.md are written well inside
  it; the two long-running items (03, 04) price their runs with the ridge law
  (§14) before starting them and sample if the full run will not fit, saying so.

- [ ] Code lives under `learning/` (or `lean/` for item 12) with a module
      docstring saying what question it answers and how to run it; runnable as
      `python -m learning.<name>`.

      §15 onwards) with: the question, the method, the baseline, the table(s),
      the finding in one paragraph, the size range covered, the kill criterion's
      verdict where the plan states one, and the regenerate command.
- [ ] `python -m pytest tests/ -q -x` passes (~80 s). New code that computes a
      quantity gets at least one test on a tiny hand-checkable instance. A new
      flag on the search gets a test that the default is unchanged.
- [ ] The item is marked `- [x]` (done) or `- [!]` (blocked, with a reason in
      PROGRESS.md) in `iterations.md`.
- [ ] No regressions, no changes to solver defaults, nothing written to
      `solutions/`. Generated instances and witnesses go under
      `learning/data/ensemble/` (committed; keep the total under ~120 MB
      apparent, and prefer a manifest of seeds to instance files). DRAT proofs
      go under `learning/data/proofs/` which item 03 adds to `.gitignore`; only
      their hashes, sizes and checker verdicts are committed.
