# TASK: Machine learning to understand the nature of MOSP — phase 2, the generated-ensemble campaign

## Philosophy
- This loop produces **findings about the problem**, not solver components. Read
  `reports/ml_nature_plan.md` §0, §2.4, §2.5, §2.8, §2.9 and §4 before anything
  else, then `reports/ml_nature.md` §1–§8 (loop0001's findings, which this loop
  builds on) and `CLAUDE.md`'s "What the corpus says about the problem itself".
  `reports/learning_plan.md` §4 lists what is closed and must not be rebuilt.
- **A prediction is never a bound.** Nothing learned may touch
  `satisfiability/mosp_solver.py::_lower_bound` or any path that decides `k`.
- **The corpus is not a sample.** loop0001 §2 showed it is a lattice of 74
  `(n, m)` cells with generator fingerprints; this loop fills the space with
  ensembles it controls, so that density can be varied at fixed size and the
  hardness and the optimum measured as functions of `(n, m, p)` rather than of
  the collection.
- **Nodes, not seconds**, for every hardness statement (`learning.node_counts.refute`
  returns them; record `config` per row as it does). Seconds beside them.
- **Deduplicate by isomorphism class** (`learning.canonical`) before counting
  anything; report both raw and per-class numbers where they differ.
- **State the size range every conclusion covers.** The campaign stops at
  `n = 40`; nothing here is evidence about 125×125 except through §2.8's
  extrapolation test, which is item 06 and says so.
- Every number in a report is regenerated by a command named in that report.
- Findings that rest on a handful of instances are re-certified for those
  instances before being written.

- **Compute**: check `pgrep -f benchmarks.recertify`; if it is running, its
  cores are not yours. 32 cores total; use up to 16 here. Each iteration has a
  hard 3-hour wall-clock cap enforced by the driver; item 01 exists to measure
  the cost of item 02 before it is spent, and item 02 samples if the pilot says
  the full grid will not fit, saying so in the report.

## Acceptance Criteria (per item)
- [ ] Code lives under `learning/` with a module docstring saying what question it
      answers and how to run it; runnable as `python -m learning.<name>`.
- [ ] A section appended to `reports/ml_nature.md` (continuing loop0001's
      numbering, §9 onwards) with: the question, the method, the baseline, the
      table(s), the finding in one paragraph, the size range covered, the kill
      criterion's verdict where the plan states one, and the regenerate command.
- [ ] `python -m pytest tests/ -q -x` passes (~80 s). New code that computes a
      quantity gets at least one test on a tiny hand-checkable instance.
- [ ] The item is marked `- [x]` (done) or `- [!]` (blocked, with a reason in
      PROGRESS.md) in `iterations.md`.
- [ ] No regressions, no changes to solver defaults, nothing written to
      `solutions/`. Generated instances and their witnesses go under
      `learning/data/ensemble/` (see Important Notes on persistence).

## Completion Conditions
An item is DONE when either:
1. **Solved**: meets all criteria and the report section is written, OR
2. **Blocked**: documented in PROGRESS.md with the specific blocker.

## Important Notes
- Do NOT run `benchmarks.csearch`, `benchmarks.recertify`, `benchmarks.overnight`
  or any sweep that writes to `solutions/`. Generated instances are solved with
  `solve_mosp_exact(..., solutions_dir=<learning/data/ensemble/solutions>)`,
  never `solutions_dir=None` and never the corpus directory.
- **Persistence**: `learning/data/` is git-ignored. The campaign's instance
  files, witnesses and the results table are the artifact of this loop and cost
  hours to regenerate, so item 01 adds a negation rule to `.gitignore` for
  `learning/data/ensemble/` (instances as `.mosp`, witnesses as JSON, results
  as CSV) and they are committed by the driver with the code. Keep the total
  under ~50 MB; if the grid is larger, commit the results CSV and a manifest of
  seeds from which the instances regenerate byte for byte.
- Do NOT edit `CLAUDE.md`; the loop's owner will fold findings in afterwards.
- Do NOT rewrite existing report sections; append. If a finding contradicts an
  earlier one, say so in the new section and leave the old one in place.
- Commit nothing yourself; the driver commits after tests pass.
- You are running in print mode: **ending your turn ends the session.** Never
  end a turn waiting on a background job or a wait/monitor. Run studies in the
  foreground (or poll them in a bounded loop) and do not stop until the report
  section, PROGRESS.md and iterations.md are written.
- When stopping a background process, match its PID or an anchored pattern,
  never a bare `pkill -f <word>` — one loop0001 iteration killed its own shell
  that way.
- Method notes inherited from loop0001 (`CLAUDE.md`): build feature sets from
  `learning.features.feature_names` group names, never from every numeric
  column (a label leaked that way and scored 1.000); never `fork` a pool after
  LightGBM has run in the parent (`spawn` with an initializer); PySR at 4
  threads and 2,000 iterations, never 16 and 10,000; round `aut_order` before
  integer division.
