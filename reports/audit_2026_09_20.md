# Audit: what this project has, and what it has never tried

**Written 2026-09-20**, after a day in which 25 cores ran flat out and closed
nothing. The point of the audit is that the day before, the same machine closed
eight instances in 28 seconds — every gain in this project has come from
changing the method, and none from running an existing one longer. That is not
an argument for stopping; NP-hard problems take time. It is an argument for
knowing which untried thing to spend the time on.

The state: **6,349 of 6,376 certified optimal (99.58%), 26 instances open**,
total gap 244 across them.

*Superseded 2026-09-22: **6,376 of 6,376 certified optimal, nothing open.** All
26 fell in a single 19.2-hour round on 25 cores — 27 files, since SP4 is stored
under two names — under Chu & Stuckey's own configuration: "better move", "old
move" and nogood recording together, with no relaxation. §5 below lists that
configuration as untried; it was the only untried item that turned out to be
needed. Eighteen of the 27 closed inside the first half hour, ten had their
upper bound improved on the way, and the last, `Random-125-125-4-2_0`, took the
full 19.2 hours and came in at 57 after entering at 60. The figures in the rest
of this document are the ones that were true when it was written and have not
been restated.*

## 2. What has never been tried

Ordered by expected value, not by effort.

### 2.1 ~~No lower bound is computed at a search node~~ — withdrawn, 2026-09-20

**This was the audit's headline item and it is wrong.** It is left here rather
than deleted, because the reasoning that killed it is worth more than the
proposal was.

The claim: the search prunes only on a candidate's immediate cost, so a node
whose remaining subproblem cannot be completed under `k` is found only by
exhausting it — add a bound on the remaining subproblem and cut the subtree.

The flaw: **any bound computed on the remaining subproblem alone is monotone
non-increasing along a path**, because the remaining set only shrinks. Cliques
get smaller; per-pattern customer counts get smaller. So a bound that does not
fire at the root can never fire at any node below it. And a bound that *does*
fire at the root proves `MOSP > k` on the spot — which is exactly what the
search was called to establish, so it is circular.

Measured before being believed: 100,000 node states sampled across random
descents of SP2's refutation at `k = 18`. The bound exceeded `k` at **zero** of
them, and the root value was 9 against a budget of 18.

A bound that is *not* monotone must involve the currently-open customers, since
they persist. The one-step version of that is **already implemented** — the
`cost <= k` filter is precisely a one-step lookahead — and deeper versions cost
as much as searching, because computing whether a completion exists two steps out
is the same question as searching two steps out.

So the search is not a branch-and-bound missing its bound. Its bound is the cost
filter, and the techniques that strengthen it are the dominance rules and the
memo, which is what Chu & Stuckey use and what is already here. That also
explains an absence in their paper that had looked like an oversight.

### 2.2 Constraint programming — and we hold the paper

`literature/martin_yanasse_pinto_2022_math_models_mosp.pdf` gives a **CP model
based on interval variables and renewable resources**, and an ILP formulation
from a graph representation. Neither has been implemented here. The CP model is
the natural formulation for this problem — an open stack *is* an interval, and
"at most k open" *is* a renewable resource of capacity k — and it is the one
shape of model this project has never built.

`ortools` is not installed. CP-SAT is a portfolio solver with a decade of work
behind it, and on a problem that maps this directly onto its primitives it is
not a long shot. It also emits its own proof logs.

### 2.3 Their nogood recording, which we assumed we had for free

`chu_stuckey_plan.md` §4 concluded "we get nogood recording free from CDCL and
should not build a nogood table". That is true of the SAT engine and **false of
the customer search**, which is now the engine closing the hard instances. Their
Table 4(a) puts nogood recording at ~1.0× once old move is on, so this is a
small prize — but the reasoning that dismissed it no longer applies.

### 2.4 Randomised restarts in the search

The search is deterministic: candidates are expanded cheapest-first, ties by
index. SAT solvers restart with randomised order because heavy-tailed runtime
distributions make a fresh start cheaper than finishing a bad one. Nothing here
tests whether this search is heavy-tailed. Cheap to try: seed the branching
order differently per worker and run the 26 in parallel replicas.

### 2.5 The customer-order encoding (plan item 1)

Never built, and the plan's reason for wanting it — symmetry removed by the
choice of variables — still stands. It is now more attractive than when it was
shelved: a *contracted* instance is small, so a customer-indexed CNF over it may
be within SAT's reach, and SAT refutations come with DRAT proofs. That would
give a checkable certificate for instances the customer search can only assert.

### 2.6 Four of the six preprocessing operations

Item reduction from pattern simplicity, and reductions from equivalent nodes and
adjacent degree-2 nodes (Yanasse & Senne 2010). Untested here. Degree-2
reduction in particular targets sparse graphs, which is what everything still
open is.

### 2.7 Relaxation used inside the search rather than before it

`relaxation.prove` needs the upper bound to already be optimal, which is why it
closes nothing. But a contraction bound computed *at a node*, on the remaining
subproblem, is the §2.1 idea with a stronger bound. Untried.

### 2.8 Two papers we hold and have not mined

- `yanasse_becceneri_soma_2007_algoritmo_exato.pdf` — an exact algorithm. Only
  its type II partial orderings were tried, as symmetry-breaking clauses, and
  they were **unsound in our encoding** and are disabled. The algorithm itself
  has not been read against what we now have.
- `goncalves_2016_brkga_mosp.pdf` — a BRKGA. Upper bounds only, but the
  stragglers have gaps of 15–20 and a better upper bound shortens every descent.

### 2.9 Parallel SAT

A `mallob` build was attempted in an earlier session and failed at 74%. Nothing
since. Cube-and-conquer over the customer search is the more promising version:
the search tree splits naturally at the root, and 25 cores are sitting on one
instance at a time.

## 3. What is not worth more time

- **More of the same descent.** 26 core-days since the last restart, zero
  progress, and the run it replaced produced nothing in its final eleven hours.
- **Theorem 2 on dense instances.** Measured, 0.44–0.49×.
- **Raising the Theorem 2 density threshold.** Measured on four completed
  refutations, all losses.
- **Porting relaxation to C.** Profiled at 0–3% of its own runtime.

## 4. The plan

1. ~~Node lower bound~~ — withdrawn on measurement, see §2.1. The slot it
   occupied is the reason to check a plan's premises before working through it.
2. **CP-SAT via the Martin/Yanasse/Pinto model** (§2.2), now the first item.
   Install `ortools`,
   implement the interval/resource model, run it against the 26. Validate the
   way everything else here is validated: exhaustive agreement on small
   instances before it is believed on large ones.
3. **Randomised restart replicas** (§2.4), which costs nothing but cores and
   tests a hypothesis nobody has tested.
4. **Then** the certificate work — VeriPB for the search, or the customer-order
   encoding for DRAT.

Items 1 and 3 are hours. Item 2 is a day. All three can run against the 26 while
the current descent continues, because they need cores at different times.
